# سياسة SEO المشتركة وخرائط الموقع

## حدود التنفيذ والسياسة المشتركة

القواعد التنفيذية موجودة في `shared/seoRules.mjs`، وهي ES Module مستقلة بلا اعتماديات. تستوردها الواجهة وBackend وأدوات Prerender مباشرة؛ ويضم Docker الملف إلى `/shared` حتى تطابق مسارات استيراد Backend. هذا أبسط من إضافة package أو تعديل lockfiles.

تتضمن حزمة managed release الآن `shared/seoRules.mjs` مع بصمة في manifest، ويقارنها التفعيل مع نسخة المصدر المستخرجة من commit نفسه. يمر الملف إلى مجلد Frontend المجاور أثناء البناء وإلى سياق Docker المحدود للـBackend؛ لا تُنسخ وثائق `shared/` أو ملفات بيئة إلى السياقين.

تحدد هذه الطبقة أهلية الفهرسة ووجهة canonical، وتوفر مولدات HTML آمنة لمحتوى SSG العام. تستخدمها Renderers في Backend للإعلانات والتصنيفات والمتاجر/الأسر المنتجة والمزادات. لا تمنح هذه الطبقة صلاحيات وصول، ولا تغيّر دورة حياة المحتوى؛ يجب أن تسبق قواعد الوصول العامة أي قرار فهرسة.

## الروابط

- النطاق الافتراضي والـcanonical: `https://souqak-yem.com`.
- يحتفظ `resolveSiteUrl` بمعاملات الاستعلام والجزء `hash` ويحظر الروابط الخارجية وبيانات الاعتماد.
- يزيل `resolveCanonicalUrl` الشرطة الختامية من المسارات غير الرئيسية، ويحذف `hash` ومعاملات التتبع المعروفة فقط. تبقى معاملات البحث والتصفية ذات المعنى؛ ويمكن لسياسة المسار أن تجعل الصفحة `noindex` دون تغيير عنوانها في المتصفح.
- معاملات التتبع تشمل `utm_*` ومعرّفات الحملات المعروفة مثل `gclid` و`fbclid`. لا يُعامل `q` أو `page` أو `categoryId` أو `sub` أو `attr_*` كمعامل تتبع.
- تبنى روابط الإعلان عبر `buildAdPath`: معرف ObjectId صالح جزء إلزامي من المسار، والـslug العربي أو الإنجليزي يرمّز مرة واحدة. إذا تكرر slug فالمعرف يبقي الرابط فريدًا. عند slug مفقود أو مشوه يُختار slug العنوان، ثم `ad`.
- السلاسل المطلقة أو `//host` لا تُقبل إلا إذا بقيت على أصل الموقع المحدد؛ لا تستخدم مدخلات المستخدم لبناء وجهة إعادة توجيه.

## أهلية المحتوى

| النوع | السياسة |
|---|---|
| الإعلانات | يلزم ObjectId صالح، `status: approved`، انتهاء مستقبلي صالح، وعدم الحذف أو الإخفاء أو الأرشفة أو البيع (`sold` أو `isSold`) أو عدم التوفر. الإعلان ذو النشر المجدول لا يفهرس قبل موعده، والمخزون المدار يلزمه رصيد موجب. |
| التصنيف الرئيسي | يفهرس إذا كان نشطًا ورئيسيًا وله اسم ووصف تحريري غير فارغ، حتى إن لم يحتوِ إعلانات. لا يُنشأ وصف بديل آليًا. |
| التصنيف الفرعي | يفهرس تدريجيًا: يجب أن يكون نشطًا وابنًا مباشرًا لتصنيف رئيسي نشط، وله وصف مفيد من ثلاثة كلمات على الأقل ومميز عن الأب والأشقاء، ويبلغ عدد إعلاناته العامة حد `minimumPublicAds` (الافتراضي 1). الحد قابل للضبط من استدعاء القاعدة ولا يجوز خفضه عن 1. معامل `?sub=` القديم يُطابق canonical المسار عند اختياره وحده؛ أي تصفية أخرى أو صفحة فارغة تكون `noindex`. |
| المتجر / الأسرة المنتجة | صفحات المتجر العامة المؤهلة تعتمد على متجر نشط واشتراك نشط كما يشترط endpoint العام. صفحات البائع الشخصية لا تُفهرس اعتمادًا على الدور وحده. صفحة المتجر غير المفلترة مؤهلة، أما البحث والتصنيف والصفحات ذات معاملات الاستعلام فتكون `noindex`. نسخة PWA مخصصة لا تفهرس؛ لا تتغير آلية PWA أو Service Worker. |
| المزادات | تفهرس تفاصيل المزاد المعتمد والمعلن للعامة في حالة `live` فقط، عند `startAt <= now < endAt`. `scheduled` و`ended` و`draft` و`cancelled` و`rejected` مستبعدة، مع بقاء الوصول والعرض كما هما. الـAPI العام يتحقق من الاعتماد وأهلية النشر قبل إرجاع التفاصيل، ولا يكشف `reviewStatus` في استجابته؛ لذلك واجهة التفاصيل تمرر نجاح الوصول العام صراحةً للقواعد المشتركة، مع بقاء فحص الحالة والوقت إلزاميًا. |
| الخدمات والحجوزات | دليل `/bookings` العام يبقى صفحة ثابتة. توجد قاعدة أهلية تجهيزّية للخدمة: `approved` ومتاحة للعامة وبها اسم ونوع ووصف؛ لا تنشئ صفحة تفاصيل أو API جديدًا، ولا تصدّر الهاتف أو الإحداثيات أو بيانات المالك. |
| صفحات البائعين | `/user/:id` و`/s/:id` غير مفهرسة افتراضيًا، بما فيها المسارات القديمة. |
| البحث والتصفية | `/search` ونتائج التصفية غير مفهرسة. لا تحذف معاملات التطبيق الوظيفية من رابط المستخدم. |
| تسجيل الدخول والحساب والإدارة | غير مفهرسة. |
| المسار غير المعروف | يصنّف كغير موجود/غير مصنف، ويكون `noindex` افتراضيًا. |
| الروابط القديمة | `/product/:id` و`/ads/:id` و`/ad/:id` بدائل غير مفهرسة؛ صفحة الإعلان تختار مسار `/ad/:id/:slug` canonical وتحافظ على `ref` الوظيفي في التحويل. |
| PWA | لا تغيّر قواعد PWA الحالية. سياق تطبيق المتجر مخصص وغير مفهرس، ومسارات `/s` تبقى غير مفهرسة. |

`classifySeoResource` يحفظ تمييزًا صريحًا بين `not_found` و`not_public` و`not_indexable` و`temporary_error` و`indexable`. يطلب Dynamic Renderer HTML للصفحات الديناميكية من قالب الإصدار نفسه، ويتحقق من القالب والأصول قبل استخدامه، ثم يرسل `robots` وcanonical ومحتوى HTML الأولي بعد فحص المورد وقواعد الوصول. يظل React يطبق `noindex` للمسارات الديناميكية في SPA/التحميل المباشر، لكنه لا يستبدل توجيه HTML الموثوق عندما تطابق قيمة `souqak-prerendered-path` مسار الطلب الأولي؛ لذلك تحفظ هذه القيمة المسار المطلوب الفعلي (بما فيه الشرطة الختامية أو معامل `sub` القديم)، بينما يبقى canonical مطبعًا. لا تعتمد الفهرسة على إزالة `noindex` بواسطة JavaScript. المورد غير الموجود وغير العام يعاد كـ404 غير قابل للفهرسة، وأخطاء قاعدة البيانات/القالب المؤقتة كـ503 مع `noindex` و`Retry-After`، ولا تعرض تفاصيل داخلية. لا يغير هذا Renderer صلاحيات API أو يوسع نطاق البيانات العامة.

## حالات الإعلان

لا تساوي السياسة بين الحالات: `approved` وحدها تمر من شرط الحالة، ثم تُستبعد الإعلانات المنتهية أو المجدولة للمستقبل أو المباعة أو المؤرشفة أو المخفية أو غير المتاحة. `pending` و`admin_draft` و`rejected` و`expired` و`sold` و`archived` و`deleted` و`blocked` و`reported` لا تمر. لا يوجد status مستقل باسم «موقوف» في نموذج الإعلان؛ حالة عدم التوفر (`isAvailable: false`) مستبعدة، وتظل حالات أخرى غير `approved` مستبعدة تلقائيًا.

لا تعدل هذه السياسة endpoint الوصول أو دورة الحالة. يلزم لاحقًا توحيد أي اختلاف متبقٍ بين استعلامات واجهات العرض العامة وسياسة SEO ضمن تغيير منفصل لا يوسع الوصول.

## التناقضات التي عولجت

- كان للواجهة وPrerender وBackend أكثر من منشئ slug؛ كما كان بعضها يشتق slug من العنوان فقط بينما يفضّل آخرون slug المخزن.
- أهلية الإعلان في الواجهة لم تفحص `isSold` أو موعد النشر المجدول، بينما فحص تصدير Prerender المخزون بصورة منفصلة، وStructured Data كان يملك شروط عرض مستقلة.
- canonical كان يحذف كل query string، بما يشمل معاملات ذات معنى؛ بينما تتطلب وظائف البحث والتصفية بقاءها في الرابط.
- endpoint معاينة المشاركة لم يطبق كل شروط الأهلية نفسها.
- Sitemap Backend كانت تعتمد على ترويسة `Host` وتضمّن إعلانات بلا فحص كامل للحذف/الإخفاء/الانتهاء، وبحد 1,000 إعلان؛ أما Prerender فكان ينتج URL Set مستقلًا بحد صفحات الإعلانات. أصبحت Sitemap Backend فهرس خرائط مجزأة، مع مصدر نطاق ثابت وأهلية مشتركة. تبقى نسخة Prerender المحدودة Snapshot للإصدار فقط ولا تمثل الخريطة الحية.
- صفحات التصنيفات في خطة Prerender لم تشترط وجود إعلانات عامة؛ وصفحة التصنيف في الواجهة لم تربط الفهرسة بالتصفية أو كون التصنيف رئيسيًا.
- سياسة `robots` في App كانت قائمة منفصلة عن التصنيف العام للمسارات؛ أصبحت تستخدم دالة المسارات المشتركة مع إبقاء سياق PWA الحالي.

## قرارات المالك المطبقة وأسئلة لاحقة

- التصنيفات الرئيسية ذات الوصف التحريري المفيد مؤهلة حتى دون إعلانات؛ والفرعية تضاف تدريجيًا عند استيفاء وصف مميز ومحتوى عام فعلي. حد الإعلانات الافتراضي 1 وقابل للرفع عند الحاجة دون تغيير شرط جودة الوصف.
- الإعلانات المباعة والمنتهية مستبعدة من الفهرسة والـSitemap والـOffer في Structured Data، دون تغيير endpoint أو تجربة عرضها الحالية.
- صفحات الحسابات التجارية العامة المؤهلة تعني صفحة متجر عام نشط ذي اشتراك نشط. لا يُفهرس `/user/:id` أو `/s/:id` لمجرد دور البائع.
- المزادات النشطة ضمن نافذة الوقت فقط مؤهلة، مع عدم تغيير الوصول للمزادات المنتهية.
- أهلية تفاصيل الخدمات العامة معتمدة، لكن لا يُنشأ مسار تفاصيل جديد في هذه المرحلة. لا يوجد حاليًا مسار HTML عام موثوق لتفاصيل الخدمة؛ يلزم لاحقًا تنفيذ المسار وربطه بالـAPI العام وبحقول `name` و`type` و`note` المصرح بها، دون إضافة حقول اتصال أو موقع إلى بيانات SEO. قرار عدم توسيع بيانات البائع/الخدمة قرار معتمد، وليس سؤالًا تجاريًا مفتوحًا.

## استخدام لاحق

- **Dynamic Renderer:** موارد الإعلانات والتصنيفات والمتاجر/الأسر المنتجة والمزادات تطبق الفلاتر العامة الحالية وقواعد الأهلية المشتركة. لا تتوفر حاليًا صفحات تفاصيل HTML عامة للخدمات أو البائعين؛ يتطلب ذلك مسارات وبيانات مصدر عامة موثوقة ومراجعة مستقلة، ولا يجوز إنشاء مسارات أو كشف بيانات اتصال/موقع ضمن هذا العمل. مسارات `/store/:id` ذات ObjectId تبقى بيد تطبيق المتجر/PWA، ولا يُفهرس سياق PWA.
- **Sitemap:** Backend يقدّم الآن الفهرس والخرائط الحية للتصنيفات والإعلانات والمتاجر والمزادات، وفق شروط الوصول والأهلية. احتفظ بقائمة المسارات الثابتة، ولا تضف تركيبات البحث أو الفلاتر. استخدم عنوان النطاق الثابت و`buildAdPath`. نسخة Prerender URL Set محدودة للإصدار غير بديل عن الخرائط الحية.

## Sitemap وrobots.txt

- يولّد Backend `/sitemap.xml` كـSitemap Index، مع خرائط منفصلة للمسارات الثابتة والتصنيفات والإعلانات والمتاجر/الأسر المنتجة والمزادات. ملفات الأجزاء مرقمة مثل `/sitemap-ads-1.xml`، ولا تتضمن خرائط البحث أو معاملات التصفية.
- تُبنى الخرائط من cursors ومجاميع MongoDB مع joins لأهلية الاشتراكات والمالكين والتصنيفات؛ لا يُنفذ استعلام منفصل لكل إعلان أو مزاد. تظهر فقط الحقول اللازمة لبناء المسارات أو التحقق من سياسة النشر، ولا تدخل حقول الاتصال أو بيانات الوثائق في مخرجات XML.
- الحد الافتراضي لكل جزء 5,000 رابط و8 MiB، والحد الإجمالي المؤقت 512 MiB، والمدة القصوى للتوليد 90 ثانية، وعدد التصنيفات النشطة 20,000. عند تجاوز حد، أو فشل قاعدة البيانات، يفشل التوليد كاملًا برسالة 503 و`Retry-After`؛ لا تُعاد خريطة قديمة ولا تُحذف روابط بصمت. تُحفظ الأجزاء في مجلد مؤقت خاص بالعملية وتُحذف عند استبدال اللقطة أو إغلاق الخدمة.
- cache الافتراضي 60 ثانية، ويُضبط عبر `SEO_SITEMAP_CACHE_TTL_MS` ضمن 1–300 ثانية، ويقصر تلقائيًا حتى أقرب انتهاء إعلان أو مزاد أو اشتراك. يُرسل ETag مبنيًا على محتوى كل ملف، وتدعم الطلبات `HEAD` و`If-None-Match`. لا يضاف `lastmod` أو `changefreq` أو `priority`: تواريخ التحديث الحالية لا تثبت تعديلًا ذا معنى SEO، وقد تتغير بسبب الإحصاءات والمزايدات وإجراءات داخلية.
- المصدر الديناميكي يستخدم النطاق الثابت `https://souqak-yem.com` ولا يشتق Sitemap من ترويسة `Host`. `generateRobotsTxt` هو المصدر المشترك لـBackend وPrerender؛ يسمح بتحميل `/assets/` و`/uploads/` ويمنع مسارات الحساب والإدارة وواجهات API. صفحات `noindex` العامة مثل البحث وصفحات البائع القديمة تبقى قابلة للزحف حتى يستطيع محرك البحث قراءة توجيه `noindex`؛ robots.txt ليس آلية صلاحيات أو حماية للبيانات.
- الحد الأدنى لإعلانات التصنيف الفرعي الافتراضي 1 وقابل للضبط عبر `SEO_MIN_PUBLIC_ADS_FOR_SUBCATEGORY` في Backend والبناء. يبقى الوصف المفيد والمميز ووجود الأب النشط شروطًا مستقلة. في بناء Snapshot، لا يتجاوز الدليل المحلي عدد الإعلانات العامة الصالحة المصدّرة؛ لذلك قد لا يُولّد صفحة فرعية حين يكون الحد مضبوطًا أعلى من البيانات المتاحة في Snapshot، بينما يحسب Backend المجموعة المؤهلة كاملة.
- Sitemap الناتجة من Prerender تبقى خريطة `urlset` خاصة بصفحات الإصدار وSnapshot، وليست بديلًا عن Sitemap Backend. يزيل Prerender تواريخ `lastmod` غير الموثوقة. يجب أن يوجّه تكامل HTTP الفعلي `/sitemap.xml` و`/sitemap-*.xml` إلى Backend الديناميكي قبل fallback للملفات الثابتة. لم تُعدّل Nginx أو ملفات النشر في هذا العمل؛ لذلك لم يثبت بعد أن الطلبات الإنتاجية ستصل إلى الخدمة الديناميكية بدل نسخة Prerender الثابتة.

## التخزين المؤقت لـDynamic Renderer

- يستخدم Backend Cache داخليًا محدودًا بلا Redis أو اعتماديات خارجية.
- عناصر Cache لا تتجاوز إعدادات العدد والبايت وحجم العنصر المفرد؛ الإخلاء LRU والتنظيف عند الاستعلام أو الكتابة.
- المفاتيح تعتمد نوع المورد والمعرّف/الـslug canonical ولا تتضمن Host أو المستخدم أو Cookies أو Authorization.
- معاملات UTM ومعرفات التتبع لا تنشئ مفاتيح إضافية. الفلاتر والمعاملات ذات المعنى تتجاوز Cache.
- القيم الافتراضية: إعلان 60 ثانية، تصنيف 120 ثانية، متجر/أسرة منتجة 60 ثانية.
- لا يُخزن HTML للمزادات؛ يتطلب الطلب إعادة التحقق من الحالة والوقت.
- لا تُخزن استجابات 503 أو 404 أو noindex أو redirect أو صفحات مخصصة لمستخدم.
- إبطال شامل آمن يتم بعد نجاح عمليات كتابة API؛ هذا يلغي HTML العام ولقطة Sitemap ويمنع إعادة تخزين Promise بدأت قبل الإبطال.
- عند تعدد عمليات Backend، الإبطال المحلي لا يُضمن وصوله لعملية أخرى؛ لذلك Cache غير ضروري لشرط الخصوصية ويجب أن تبقى إعادة التحقق في كل مورد حسّاس.
- يستخدم Renderer سياسة `no-store` ولا يعتمد Cache المتصفح أو Nginx أو CDN في هذه المرحلة.

إعدادات البيئة:

- `SEO_RENDER_CACHE_ENABLED=true`
- `SEO_RENDER_CACHE_AD_TTL_MS=60000`
- `SEO_RENDER_CACHE_CATEGORY_TTL_MS=120000`
- `SEO_RENDER_CACHE_STORE_TTL_MS=60000`
- `SEO_RENDER_CACHE_AUCTION_TTL_MS=10000`
- `SEO_RENDER_CACHE_MAX_ENTRIES=2000`
- `SEO_RENDER_CACHE_MAX_BYTES=67108864`
- `SEO_RENDER_CACHE_MAX_ITEM_BYTES=524288`
- `SEO_RENDER_CACHE_MAX_IN_FLIGHT=256`

يجب على التشخيص والتكامل المتعدد العمليات إبقاء القيم ضمن الحدود الموضوعة؛ لا يعدل TTL فعليًا موعد انتهاء المورد أو اشتراكه.

## عزل اختبارات Prerender

عند ضبط `SEO_PRERENDER_TEST_MODE=true` أو `1`، يرفض `getPrerenderData` أي مصدر غير `local` قبل استدعاء محمّل API. استخدم هذا المفتاح مع `SEO_PRERENDER_DATA_SOURCE=local` وSnapshot اصطناعية محلية، ووجّه `SOUQAK_VITE_ENV_DIR` إلى مجلد مؤقت فارغ حتى لا تُحمّل ملفات `.env`؛ يمكن إبقاء وضع Vite `production` لاختبار بناء مطابق للإصدار بأمان. يمكن توجيه ناتج البناء إلى مجلد مؤقت مع `SOUQAK_BUILD_DIST_DIR`؛ مسار API الإنتاجي في تجهيز الإصدار ومسار `dist` الافتراضي لم يتغيرا.

## المخاطر والتحقق اللاحق

- يلزم في التكامل النهائي التحقق من أن Nginx/طبقة التوجيه تخدم Sitemap Index وملفات الأجزاء من Backend، وألا تتقدم ملفات `frontend/dist` على المسارات الديناميكية. لم يتم الاتصال بـVPS أو تعديل إعداداته.
- يلزم اختبار MongoDB المتوافق مع `$lookup` ذي pipeline ووقت التشغيل الفعلي تحت حمل بيانات واقعي؛ اختبارات الوحدة تستخدم cursors وبيانات اصطناعية ولا تشغل قاعدة بيانات.
- يجب مراقبة حدثي `sitemap_generated` و`sitemap_generation_failed` وأحجام الخرائط وأزمنة توليدها، ثم ضبط حدود الموارد بناءً على القياس دون إسقاط روابط بصمت.
